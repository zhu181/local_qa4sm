# QA4SM Local Validation

## Quick start
- Run: `uv run qa4sm-validate <config.json>` (config arg optional; defaults to `validator/validation_run.template.json`)
- Or: `uv run python -m validator.cli <config.json>`; dry-run: `--dry-run`
- Windows helper: `.\run_validation.ps1 [<preset>] [-Config PATH] [-BBox lat0,lon0,lat1,lon1] [-Gpu] [-MemoryLimit SIZE] [-Heartbeat SEC] [-EnvVar NAME=value] [-DryRun] [-LogLevel X] [-LogFile PATH] [-MaxWorkers N] [-Interactive]` (uses `.venv\Scripts\python.exe`)
  - Preset names are fuzzy-matched against `presets/validation_run.*.json` (e.g. `ismn-spl3`, `spl3smpe`); `-List` shows them
  - `-BBox` overlays `min_lat/min_lon/max_lat/max_lon` onto a temp copy (keeps full-preset runs small/fast) and deletes it after a real run
  - `-Gpu` sets `QA4SM_USE_GPU=1`; `-MemoryLimit` sets `QA4SM_DASK_MEMORY_LIMIT` (e.g. `16GB`) **and persists the value to `outputs\.dask_memory_limit`** so later runs without the flag reuse it (env vars don't survive restarts — without this a fresh shell silently fell back to 4GB/worker); when no flag and no persisted value the script defaults to `16GB` total. `-Heartbeat` sets `QA4SM_HEARTBEAT_INTERVAL_SECONDS`; `-EnvVar` is a repeatable `NAME=value` passthrough; unset vars are cleared so no stale env leaks between runs; `-Config` still accepted for explicit paths
  - Every invocation writes a timestamped log to `logs\validation_run_<ts>.log` by default (script-level events + validation output in one file; dry-runs too) unless `-LogFile` overrides it; script prints the path at the end
  - `-Interactive` prompts through preset/bbox/GPU/memory/dry-run choices (GPU defaults ON) then confirms before running

## Config
- JSON config; `reader` selects the reader class by string name (e.g. `"SMAPL3_V9Reader"`, `"ISMN_Interface"`, `"GriddedNcOrthoMultiTs"`), NOT by dataset short_name
- `storage_path` must point to your own local data dirs (CLI fails fast if missing); `SMAPTs` reader also requires `grid.nc` there

## CLI & env
- `qa4sm-validate [config] [--dry-run] [--log-level {DEBUG,INFO,WARNING,ERROR,CRITICAL}] [--log-file PATH] [--max-workers N]`
- Env: `QA4SM_MAX_PARALLEL_WORKERS` (default = min(2, CPU count)), `QA4SM_HEARTBEAT_INTERVAL_SECONDS` (default 60), `QA4SM_USE_GPU`, `QA4SM_DASK_MEMORY_LIMIT` (total budget for all workers, e.g. "16GB"; divided equally per worker; default 4GB per worker), `QA4SM_DASK_BATCH_SIZE` (gpis per Dask batch; default 25 — a 100-gpi ISMN×SMAP batch can peak >11 GB and OOM the worker; smaller batches avoid nanny restarts that kill in-flight batches)
- Classic path: `ThreadPoolExecutor`; ISMN reference reader forces `max_workers=1` (not thread-safe)
- Repetitive log/warning noise auto-suppressed after first 5 occurrences; pytesmo logger forced to CRITICAL; `dask`/`distributed` loggers forced to WARNING so their INFO chatter doesn't drown validator output
- Progress is logged to the log file (not just tqdm-to-stderr): GPU/Dask path logs `GPU/Dask progress: <done>/<total> gpis (<pct>%) elapsed=… ETA≈…` at INFO every ~15 s plus 25/50/75/100% milestones; classic path heartbeat includes ok/error counts + ETA
- `run_validation.ps1 -MemoryLimit` accepts a bare number (e.g. `8`) and normalizes it to `8GB` (logs the assumption); a bare int passed to Dask is an invalid memory spec. The last explicit value is persisted to `outputs\.dask_memory_limit` and reused when the flag is omitted; without any persisted value the script defaults to `16GB` total

## GPU acceleration
- pytesmo metrics auto-dispatch to CuPy when available (`_GPU_AVAILABLE` checked at import); no per-call wiring needed
- `QA4SM_USE_GPU=1` switches to the Dask-parallel GPU path (single `Validation.calc(..., parallel="dask", use_gpu=True)`); if GPU/CuPy is unavailable it logs a warning and falls back to the classic threaded path
- **Memory-bounded streaming (M3/E4)**: the GPU path streams results in batches instead of accumulating everything in the client.
  - `Validation.calc(..., batch_callback=fn)`: dask branch routes through `_run_streaming` → `executor.map_batches_streaming`; each completed batch is compacted (`_compact_batch`) and handed to the callback, then released. `calc()` returns a small summary dict `{"n_gpis", "batches", "keys"}` instead of full results (backward compatible — without `batch_callback` it returns the full merged dict as before).
  - qa4sm `_run_gpu_dask_validation` passes a callback that converts each batch (`_pytesmo_to_qa4sm_results`) and appends it to the run netCDF (`check_and_store_results`), so peak client/worker memory is ~one batch (`batch_size=settings.DASK_BATCH_SIZE`, default 25).
  - **Worker-death tolerance**: `distributed.scheduler.allowed-failures` is raised to 10 (pytesmo `parallel.py` dask.config block) so a batch lost to a nanny OOM restart is retried on a fresh worker instead of being marked failed after 4 worker deaths. This is belt-and-braces; the real fix is the smaller default batch size (25) which keeps a 100-gpi ISMN×SMAP batch from peaking >11 GB.
  - **Crash-resume cache**: completed batches are persisted client-side to `outputs/.dask_batch_cache/<sha1(config)>_b<batch_size>/batch_<i>.zarr/` (per-combo zarr groups + `combos.json` + `metrics.json` + `.complete` sentinel written last). Same config re-run skips done batches; any config change (datasets/interval/bbox/metrics) **or batch-size change** (`DASK_BATCH_SIZE`) gets a fresh cache dir — batch boundaries depend on the batch size, so reusing a cache written with another size would misalign gpis across batches. The pytesmo resume path also length-checks each cached batch against the current batch (`pytesmo/src/pytesmo/parallel.py`, covered by `test_map_batches_streaming_resume_batch_size_mismatch`) and recomputes mismatches as belt-and-braces. Cache is per-config and persists across runs; no cleanup yet. The batch store handles the real per-gpi result structure `{combo: [{metric: array}, ...]}` (list of per-window metric dicts); error gpis are positionally aligned as absent on reload. Metric names with filesystem-incompatible characters (e.g. `2016|BIAS`) are sanitized for zarr DirectoryStore with a `metrics.json` mapping. The config hash must stay stable across runs: model back-ref fields (`DatasetConfiguration.validation`, `ParametrisedFilter.dataset_config`) are `repr=False` and `_config_hash` drops callables (the parser attaches a bound `save` method whose repr embeds the per-run UUID — without this the hash changed every run and resume never hit).
  - Worker memory fractions are set via `dask.config` (`distributed.worker.memory.{target,spill,pause,terminate}`, defaults 0.7/0.7/0.9/0.95) — modern distributed no longer accepts them as `LocalCluster` kwargs; qa4sm passes `memory_target_fraction=0.6, memory_spill_fraction=0.55` via `parallel_kwargs`, and the config propagates to worker subprocesses at startup.
- Dask worker `memory_limit` is set explicitly (default 4 GB per worker) because Dask's `auto` (~40%) triggers `KilledWorker` on memory-hungry readers (e.g. `GriddedNcOrthoMultiTs` reads add ~1 GB RSS per gpi). Default worker count is2 (caps parallelism so each worker gets more physical RAM). Override via `QA4SM_DASK_MEMORY_LIMIT` (total budget, divided per worker) and `QA4SM_MAX_PARALLEL_WORKERS`
- Root venv uses Python 3.13 + `cupy-cuda13x==14.1.1` (matches the installed CUDA 13.3 toolkit; the only `cublas64_12.dll` on this machine is a stale app bundle that fails to load, so `cupy-cuda12x` cannot do tcol/matmul). **Never install both `cupy-cuda12x` and `cupy-cuda13x`** — they share the `cupy`/`cupy_backends` namespace dirs and clobber each other's bundled CUDA DLLs: cupy still imports (runtime reports 12.x) but `cupy_backends.cuda.libs` loses its `.dll` files and `matmul`/tcol fails with `ImportError: DLL load failed while importing cublas`. Recovery: `uv pip uninstall cupy-cuda12x && uv pip install --reinstall cupy-cuda13x==14.1.1`, then re-pin `numpy==2.4.6` (cupy bumps to 2.5.x, breaking numba). Note the fixed env reports CUDA runtime 13.2 (13020) and loads `cublas64_13.dll` from the system CUDA 13.3 toolkit via PATH.
- On this machine Dask auto-limits to 1 worker (1 GPU); the win is GPU-accelerated metric/bootstrap compute, not multi-worker parallelism
- **Dask cluster-teardown timeout is non-fatal**: after the last batch completes, `LocalCluster` may take >4s to kill a worker and raise `TimeoutError` ("Worker process still alive after 4.0 seconds, killing") from `executor.close()`. Two defenses: (a) pytesmo `DaskParallelExecutor.close()` catches/logs close errors instead of raising; (b) qa4sm `_run_gpu_dask_validation` treats an exception after `state["ok"]+state["error"] == n_gpis` as success (results already streamed to netCDF) instead of falling back to the classic path, which would discard finished results.
- Verified on real data (SPL3SMPE x NSMCSMC, 132 points with bbox): Dask+GPU streaming path runs end-to-end (~34 s validation, ~2 min total), 132/132 ok, 0 errors, output netCDF + plots. Resume verified: second run with same config loads 2 cached batches and completes correctly.
- ISMN presets (ISMN x SPL3SMPE x NSMCSMC, 68 stations, tcol=True) also verified end-to-end on both classic and Dask+GPU paths (41/41 ok on valid stations; remaining 27 = stations outside the 2017-2021 interval). Required fixes: tcol `refname` must be the prefixed spatial-ref name (`0-ISMN`), missing `frm_class` metadata filled with template defaults instead of raising, and stability-adapter status keys (`bulk|status`) recognized in pytesmo error paths
- ISMN+tcol bbox run (bbox `38,-110,43,-104`, 1019 stations) verified on both paths: 329 ok / 690 error. The 690 errors are genuine data gaps (684 status 7 = station has no data in the 2017-2021 interval, 6 status 1 = insufficient obs), NOT computation failures; all 3 combos (2 pairwise + tcol triple) are status 0 on the 329 valid stations, and tcol `snr`/`beta`/`err_std` + pairwise `R` are bit-identical between classic and Dask+GPU runs. Before the cublas fix this config reported 1019/1019 errors with tcol status 2 (METRICS_CALCULATION_FAILED) everywhere.
- **qa4sm_reader transcriber only keeps tcol metrics for the hard-coded `DATASETS` list** (`qa4sm_reader.globals.DATASETS`, e.g. ISMN is there but SPL3SMPE/NSMCSMC are not). Without intervention the transcribed netCDF silently drops `beta`/`snr`/`err_std` for datasets outside that list, keeping only `0-ISMN`. Fixed via monkeypatch: `validator/validation.py::_extend_transcriber_datasets` appends the run's dataset short names to `qa4sm_reader.netcdf_transcription.DATASETS` (the module namespace `is_valid_tcol_metric_name` reads at call time) before transcription in `_post_process_run`. Patching `qa4sm_reader.globals.DATASETS` alone does NOT work — the method reads the imported copy in `netcdf_transcription`.
- The two `ERROR | tornado.application` lines in run logs ("Unable to allocate 2.95 EiB for an array with shape (...)") are benign Dask TCP-handshake noise (a connection closes mid-read, garbage frame length) — they don't affect results and are intentionally NOT silenced.
- Tcol metrics (`snr`/`beta`/`err_std`) intentionally produce NO comparison/box plots: `plot_all.py:62` excludes `metric_groups['triple']` from clustered boxplots; only overview maps + `tc_status` barplot are generated for the tcol combo.

## Architecture notes
- Entrypoint: `validator/cli.py:main`; flow: `orchestrator.parse_validation_run_config` → `validation.run_validation`
- Models are in-memory dataclasses mimicking Django ORM: `ValidationTask.objects.filter()/.get()/.save()/.delete()` (no DB)
- Output dir: `outputs/` (`settings.py:MEDIA_ROOT`); stale `.nc` files in run dir auto-cleaned on re-run
